# Bonding Club

A private mobile-first quiz for **exactly 20 friends, 20 personal questions, and 20 gifts**. Built with Next.js App Router, TypeScript, Drizzle ORM, and Supabase-hosted PostgreSQL. The browser never accesses Supabase directly.

## Requirements

- Node.js 20.9+ (Node.js 22 LTS recommended), npm, and an existing Supabase project.
- A PostgreSQL connection for the server and a direct/session-pooler connection for migrations.
- HTTPS for production. Phones must be able to reach the same deployed URL.

## Set Up

```sh
npm ci
cp .env.example .env
```

Set these **server-only** values in `.env` locally and your hosting provider's secret environment configuration in production:

| Variable              | Purpose                                                                                                                             |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`        | Supabase PostgreSQL runtime URL. Transaction pooler port 6543 is supported; prepared statements are disabled.                       |
| `DIRECT_DATABASE_URL` | Supabase direct URL or session pooler port 5432 for migration execution. Falls back to `DATABASE_URL` if absent.                    |
| `APP_URL`             | Exact origin of the app, e.g. `https://quiz.example.com`. Used for invitations and cross-origin-write protection. No trailing path. |
| `HOST_PASSWORD_HASH`  | Scrypt password hash generated by the command below. Never a plaintext password.                                                    |
| `CRON_SECRET`         | Optional >=32-character secret for scheduled deadline reconciliation.                                                               |

Get connection strings from Supabase's Connect dialog. URL-encode special characters in passwords; use encrypted connections (`sslmode=require`). Runtime credentials must be the table-owning PostgreSQL role or a deliberately configured trusted server role with appropriate grants and RLS bypass. Do not use `anon`/`authenticated` for runtime SQL. No service-role API key or `NEXT_PUBLIC_*` database secret is needed.

Generate a host hash without putting the password in shell history (example for zsh):

```sh
read -s 'quiz_password?Host password (at least 12 characters): '
printf '%s\n' "$quiz_password" | npm run host:password
unset quiz_password
```

Copy only the resulting `HOST_PASSWORD_HASH=...` line into the environment. Changing this hash invalidates old host sessions on the next request. The generated hash is a server secret too.

## Content and Database Initialization

`src/seed/data.ts` contains the supplied 20 participant names, questions, four options and answer keys. Stable IDs must remain unique. The answer keys and private questions are sensitive: do not publish the source or CSV before the event. Gift metadata is a generic placeholder because gift contents are unknown; it is stored server-side and never sent to participant or host browsers.

```sh
npm run db:generate  # Only when intentionally changing the Drizzle schema.
npm run db:migrate
npm run db:seed
npm run db:check
```

Committed migrations create eleven `bq_*` tables with foreign keys, indexes, checks, immutable-submission uniqueness, one gift per recipient, and one allocation per gift. Migration records are isolated in the `bq_drizzle` schema. The migration command inspects existing quiz table names, then applies only unapplied migrations. No manual dashboard table creation, `push`, `DROP`, `TRUNCATE`, reset, or startup seed is used.

Before applying migrations to your Supabase project, take a backup and review `drizzle/*.sql`, especially if the project already has tables named `bq_*`. The initial migration fails rather than replacing colliding tables. Existing unrelated schemas and migration histories are not touched.

The 20-person event requires `0003_twenty_participants.sql`. This migration changes quiz constraints and does not reset data. An existing initialized 21-round event or round 21 prevents the migration from applying; preserve it or arrange a separate fresh event database before migrating. Existing placeholder content is never silently overwritten by the seed command. This app does not automatically reset data or invitations.

The matching seed can be rerun without modifying results, order, sessions, or allocations. If seeded content differs, the command refuses to overwrite it. This MVP is one event, not a replay/reset tool. Use a separate database/environment for rehearsal; there is no destructive game reset command.

RLS is enabled, with no client policies; all table privileges for `PUBLIC`, `anon`, and `authenticated` are revoked. This is defense in depth, not a claim that Drizzle configures RLS automatically. No Realtime publication is configured because updates use authenticated polling.

## Generate Private Invitations

```sh
npm run invites:generate
```

The command creates `private-invitations.json` with filesystem mode `0600`, containing exactly one unique link per participant. It never prints links/tokens and refuses to overwrite an export or silently replace existing tokens. Send each person only their own link using a private channel. Keep the export out of Git, logs, screenshots, shared drives, analytics, and public hosting.

Links look like `https://quiz.example.com/join#<private-token>`. The fragment is not sent in HTTP request paths. The join screen strips it from browser history before exchanging it via a same-origin POST for an HttpOnly participant cookie. Token hashes, not raw invitation/session tokens, are stored in the database. The app has no analytics, third-party scripts, or public invitation-list endpoint.

To revoke **all** participant invitations and sessions explicitly:

```sh
npm run invites:generate -- private-invitations-v2.json --rotate
```

Redistribute the new links. Do not rotate during a live round unless you intend to disconnect everyone. Hashed tokens cannot be retrieved later; preserve the export. If export writing fails after token generation commits, resolve storage and perform an explicit rotation into a new private file.

**Bearer-link limitation:** anyone holding a participant's link can join as them. Multiple devices using the same link share the same identity and the same single immutable submission. There is no physical-person verification. One seeded identity does not imply one open browser tab.

## Run and Play

```sh
npm run dev
# Or after configuring production secrets:
npm run build
npm start
```

- `/`: landing page.
- `/join#...`: private invitation exchange or clear error screen.
- `/play`: participant lobby, active question, submitted state, results, personal gift, final gacha, and completion.
- `/host`: separately authenticated host desk, participant presence, progress, current round, results, answer log, and gift ledger.

Choose **Full Auto** on the host lobby before the first round, or leave it unchecked for the existing host-cued mode. The choice persists across refresh and cannot be changed after play starts.

### Full Auto

1. Log in, enable Full Auto, and initialize the shuffled order.
2. Give the first cue with "Mulai ronde pertama".
3. Each question accepts answers for the full **15 seconds**, even if all 19 eligible respondents have submitted.
4. Correctness and the gift winner appear automatically, followed by a **10-second results intermission** with a shared countdown.
5. The next question starts automatically. After round 20's intermission, final gacha distributes remaining gifts and the ranking opens automatically.

There are no early-close/advance controls in Full Auto. The host may disconnect: participant polling still progresses the event. If everyone disconnects and no scheduler is running, reconnection resumes from the persisted phase without skipping questions; an overdue question first gets a full results intermission and the next question gets a fresh 15 seconds. Polling/request latency may add a short delay to transitions, never shorten either phase. This mode adds `drizzle/0002_full_auto_mode.sql`: run `npm run db:migrate` before using the updated app against an existing database. It adds only a default-false mode column and does not reset or reseed anything. Existing games remain manual.

### Host-Cued Mode

Host sequence (Full Auto unchecked):

1. Log in at `/host` with the password corresponding to your hash.
2. Initialize once: the server cryptographically shuffles and persists the 20-question order.
3. Start a round. The server creates its fixed 15-second deadline.
4. Wait, or close early. Deadline expiry, all 19 non-author submissions, or early closure automatically publish the correct answer and winner. No reveal button is needed.
5. Advance, then cue the next round's start when everyone is ready. Results stay visible until you advance; the next timer never starts on its own. Repeat for 20 rounds.
6. Advance to final gacha and distribute remaining gifts. Even if no gifts remain, this verifies completion.

The author cannot answer their own question. Previous winners may answer but cannot win again. Each answer is acknowledged only after a committed server write. The winner is the first correct eligible accepted submission ordered by database receipt timestamp, then monotonic database submission ID. Client timestamps are rejected. Closure, result publication, and any gift assignment are committed transactionally. While a round is active, its key, winner, and correctness remain absent from player/host state responses.

Gift contents are never revealed: the personal card and host/final ledger show only who gives a gift to whom. Gift names and descriptions are excluded from browser responses, not merely hidden in the UI. This also applies after final gacha and on reconnect. Existing closed-but-unrevealed rounds from the previous version automatically publish their persisted results on the next trusted request without awarding gifts twice; no database migration, reseed, or reset is required for this revision.

Final gacha validates remaining counts, shuffles gifts without replacement, commits every pairing atomically, and completes only with 20 unique recipients and gifts. Repeated/concurrent gacha calls return the same persisted result. Final gacha may return a participant's own gift; the PRD did not prohibit that.

### Final Ranking

After final gacha completes the game, the host and all participants see the same ranking of all 20 participants by the number of correct answers. Each player is highlighted on their own screen. Tied scores share the same rank (for example, 1, 1, 3); player IDs provide a stable display order within a tie but do not break it. Wrong or unanswered questions contribute zero, and an author cannot answer their own question.

All correct answers count regardless of previous gift wins; answer speed does not affect ranking. Gift eligibility and the final gacha are unchanged. The ranking is returned only after `game_complete`, derived from persisted submissions, and includes players with zero correct answers. Refresh/reconnect and existing completed games work without a migration or reseed. Gift contents remain secret.

### Player Celebrations

Players get a popup and a short confetti burst when their submitted answer is revealed as correct and/or the server confirms their gift assignment, including final gacha. Simultaneous answer/gift events share one popup. Correctness is never celebrated before the result is published, and gift popups show the giver only, not contents. Hosts do not get these popups.

The popup uses a keyboard-accessible modal with a "Lanjut bermain" button and Escape dismissal, and automatically closes when the next round starts. Event IDs are remembered in per-tab session storage so polling/reload does not replay a celebration. If storage is disabled, an in-memory guard prevents polling repeats, but refresh may replay it. Reopening in a new tab can celebrate the current result again. Confetti runs briefly, then is removed; reduced-motion users still receive the popup without confetti. No sound, external animation service, or new dependency is required.

## Synchronization and Recovery

Authenticated state polling is every one second during an active round or automatic intermission and two seconds otherwise, with three-second retry after errors. It does not broadcast keys, token hashes, or session data. Refresh/reconnect reads the authoritative database state and uses the existing cookie. Participant sessions expire after seven days; host sessions after twelve hours. Presence is approximate (seen within thirty seconds), not an eligibility or registration rule.

All game reads and mutations lock the same singleton event row across server instances. Deadline checks use `clock_timestamp()` inside PostgreSQL; the insertion statement compares its single captured receipt time against the deadline. A savepoint rolls back rejected mutations while keeping safe deadline reconciliation. Browser countdowns use a monotonic display clock anchored to a server response and are never used for acceptance or ranking.

If the host disconnects, participant polling can close an expired round and publish its results automatically. If **every** client is disconnected, closure and publication happen on the next authenticated request; late answers still cannot be accepted. Connected clients see results on their next poll, normally within about one second plus request latency. For closure persistence with no connected clients, optionally schedule:

```text
GET /api/reconcile
Authorization: Bearer <CRON_SECRET>
```

The scheduler frequency determines reconciliation delay, not the answer deadline. Configure a provider-supported scheduler; it is not automatically installed. Origin checking applies to all ordinary POSTs. Host login and invitation exchange have database-backed rate limits, as do per-identity answer attempts. Limits are intentionally global for login/exchange rather than trusting spoofable proxy IP headers; use an edge/WAF rule for internet-facing abuse protection.

## Deployment

Deploy as a Node.js Next.js app (e.g. Vercel or a Node container). Do not use a static export or Edge-only runtime. Configure production secrets, run migrations and seed as a controlled one-off operation, then generate invitations with the final HTTPS origin. Use production secrets only on the production deployment, and separate Supabase credentials for previews/rehearsal.

No deployment was created automatically and no supplied Supabase database was migrated in this workspace: connection credentials were not present. The production bundle builds without connecting to a database. Server endpoints return a safe setup error until configured; there is no fake successful write or automatic in-memory fallback.

## Tests

```sh
npm run typecheck
npm test
npm run test:cli
npm run build
npx playwright install chromium
npm run test:e2e
npm run test:e2e:auto
```

Integration tests use actual SQL migrations and embedded PostgreSQL (PGlite), not an in-memory imitation of game logic. They exercise the same Request/Response handler mounted in Next.js and cover seed validation, session isolation, revoked/expired invitations, host authorization, cookie protection, cross-origin requests, duplicate/concurrent answers, author exclusion, option ownership, transitions, deadlines without the host, no key leak, winner/tie ordering, previous winners, no-winner rounds, gift uniqueness, gacha integrity/idempotency, and a complete 20-player simultaneous-answer simulation.

PGlite serializes its connection, so these tests do not by themselves prove independent-process PostgreSQL row-lock behavior or Supabase latency. For that, use a dedicated test PostgreSQL URL:

```sh
TEST_DATABASE_URL='postgresql://...' npm test
```

Each harness creates a random isolated `bq_test_*` schema and removes only that schema afterward. This requires schema-creation privileges. No existing tables are reset. Use a test project and encrypted connections, never a production URL in shell history.

Browser tests start the real Next.js app against a separately created disposable local PostgreSQL database, using `.next-e2e` build output so an existing development server can keep running. They check invalid links, mobile overflow, host-cued starts, automatic results after the host disconnects, answer/gift persistence through reload, offline/online recovery, and giver-only gift displays. Test-only local database support requires both `ALLOW_LOCAL_TEST_DATABASE=1` and `LOCAL_TEST_DATABASE_PATH` and is disabled in production. It is not a deployed storage option. Private test exports stay in the OS temporary directory; no trace recording of invitation links is enabled.

`test:e2e:auto` runs the Full Auto browser suite with its own fresh disposable event, covering persisted mode selection, host disconnect, real 15/10-second transitions, popup dismissal, reconnect, and 320/390px layouts. Run it separately from the manual suite: the app intentionally has no game reset.

## Scope and Limitations

- Gift contents remain unknown; participant names, questions and keys are private event data.
- Exactly one event; no question editor, registration, multi-event administration, reset, or sound effects.
- Polling is the MVP synchronization mechanism; updates are not instantaneous push notifications.
- Timing fairness includes real network/server latency; receipt order cannot measure the moment someone tapped on their phone.
- One serialized event lock is appropriate for 20 participants, not a high-scale multi-event service.
- Session expiration and invitation revocation are enforced, but old rows are not periodically purged. Configure maintenance outside a live game if long-term retention matters.
- Static homepage styling uses local font fallbacks, inline SVG, and CSS; no third-party asset requests are made.
- CSP permits Next.js inline scripts and development evaluation. All content is seed-controlled plain React text, never injected HTML. Tighten to a nonce-based CSP if introducing third-party/user-generated content.
